## الفلسفة التجارية (السبب الجوهري)

المالك يبيع ترويج مدفوع: المتجر يدفع ليصير في «ترند يومي/أسبوعي/أبرز». يبرّر الدفع بأن هذه الأقسام تجذب نقرات/نسخ **إضافية** مقارنة بظهور المتجر العادي. لإثبات القيمة، الأرقام في كل قسم لازم تكون **مستقلة وغير مكرَّرة** — كل حركة تُنسب لمكانٍ واحد فقط:

> «ستايلي» قبل الترند: نسخ متجر=5
> «ترند يول» بعد دخوله الترند اليومي: نسخ متجر=10 + نسخ ترند يومي=100
> الإجمالي=110 (ندخل دفعه = 100 نسخ إضافية بفضل الترويج)

## القسم 6 buckets — Mutually Exclusive

كل صف في `action_logs` يُصنَّف في **bucket واحد فقط** حسب context الدخول:

| Bucket | source data | معايير التصنيف |
|---|---|---|
| **نسخ/نقر متجر** | base | دخل من قائمة المتاجر العادية (لا story_view_id، لا context خاص) |
| **نسخ/نقر ترند يومي** | context | دخل من بطاقة الترند اليومي → `details='trend:daily'` |
| **نسخ/نقر ترند أسبوعي** | context | دخل من بطاقة الترند الأسبوعي → `details='trend:weekly'` |
| **نسخ/نقر أبرز** | context | دخل من قسم «أبرز المتاجر» (top N من المفضّلات الموحّدة) → context يحتاج تتبع |
| **نسخ/نقر ستوري عادي** | story | `story_view_id IS NOT NULL` على متجر **غير ترند** |
| **نسخ/نقر ستوري ترند** | story | `story_view_id IS NOT NULL` على متجر **في الترند** (master.is_trending أو مثبَّت) |
| **بحث** | search | `action_type='search'` (مستقل، إجمالي واحد) |

## معادلة الإجمالي

**إجمالي الحركات** = نسخ متجر + نقر متجر
                   + نسخ/نقر ترند يومي + نسخ/نقر ترند أسبوعي
                   + نسخ/نقر أبرز
                   + نسخ/نقر ستوري عادي + نسخ/نقر ستوري ترند
                   + بحث

**كل buckets تُجمَع** — لا subsets، لا overlap، لا double-counting.

## معيار «أبرز المتاجر»

- Top N من `user_favorites` (kind='store') عبر **bot + miniapp + web** موحَّداً (الأكثر تفضيلاً يتقدّم).
- N والـthreshold يُحدّد من واجهة الموقع/الميني.
- **ليس** `master.is_promoted` (هذا حقل آخر).

## التتبّع الحالي (ما المتوفّر، وما الناقص)

**متوفّر:**
- `story_view_id` على `action_logs` → يحدّد حركات الستوري بدقة.
- `action_logs.details = 'trend:daily' / 'trend:weekly'` على `click_link` عبر `/go/{slug}?ctx=...` (في `api/routers/go.py`).

**ناقص (يحتاج تطوير):**
- `copy_coupon`: لا يحفظ context حالياً. الواجهة (موقع/ميني/بوت) لا تمرّر `ctx` لـ`/track/copy` و الباك لا يحفظه.
- `أبرز` context: لا يوجد إطلاقاً — يحتاج إضافة `ctx=featured` في الواجهة وقبول/حفظ في `/go` و`/track`.

## How to apply

1. **Backend**: توسيع `action_logs.details` (أو حقل جديد `entry_context`) ليقبل: `trend:daily`, `trend:weekly`, `featured`, `null` (= store list عادي). تطبيقه في كل `/track/*` endpoints.
2. **Frontend** (موقع + ميني + بوت): تمرير `ctx` مع كل copy_coupon و click_link حسب القسم الذي صدر منه الحدث.
3. **Dashboard**: التصنيف يقرأ `details` (أو الحقل الجديد) لتحديد الـbucket. الحركات القديمة (قبل التتبع الكامل) ستظهر في «متجر عادي» تلقائياً (acceptable lossy).
4. **حذف الأعمدة القديمة المتناقضة** قبل الإضافة: «نسخ ترند» العام، أي «ترند يومي/أسبوعي» المبنية على store-attribute بدل context.

## التحفّظات

- البيانات التاريخية قبل تطبيق context tracking ستفقد التفصيل (تظهر كـ«متجر عادي»).
- التتبّع التاريخي للستوري شغّال أصلاً (لأن `story_view_id` مدعوم من البداية).
- التطبيق التدريجي: ابدأ بـ«ترند يومي/أسبوعي» (موجود جزئياً لـ`click`) ثم وسّع لـ«أبرز» و`copy_coupon`.
