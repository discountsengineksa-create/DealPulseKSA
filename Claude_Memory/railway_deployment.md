Railway project (`a6f16564-...`) runs **two services from the same GitHub repo**, each with a different build:

- **API/bot service** (DealPulseKSA, `api.dealpulseksa.com`, serviceId `db3f65bc-...`):
  builds with the **root `Dockerfile`** → installs `requirements-railway.txt` (lean, **no streamlit**) → runs `uvicorn bot_app:app`. Healthcheck `/health` (railway.toml). Python 3.12. This serves the API + bot webhook + `/miniapp`.
- **dashboard service** (`3e0abceb-...`): builds with **`Dockerfile.dashboard`** (pinned via the service's **Settings → Config File = `railway.dashboard.json`**) → installs full `requirements.txt` (has streamlit) → runs `streamlit run dashboard.py`. **Must use Python 3.13.**

**Gotchas (cost a long debug on 2026-05-28):**
- `requirements.txt` is a **Python 3.13 freeze** — it pins 3.13-only stdlib-removal backports (`audioop-lts`, `standard-aifc/chunk/sunau`). Building it on Python 3.12 fails: "No matching distribution for audioop-lts". The dashboard image therefore pins `python:3.13-slim`. (`requirements-railway.txt` is lean and 3.12-safe for the API.)
- Railway kept **auto-picking the root `Dockerfile`** (API image, no streamlit) for the dashboard → intermittent `streamlit: not found`. Fixed by a dedicated `Dockerfile.dashboard` + per-service Config File. Don't rely on the `builder=RAILPACK` value in the config file — it wasn't honored reliably; an explicit `DOCKERFILE` + `dockerfilePath` is deterministic.
- Streamlit **CORS warning** (`enableCORS=false incompatible with enableXsrfProtection=true`) is a red herring — it's just a warning, app still works. Real fix = **don't set `enableCORS=false` anywhere** (command flags, Procfile, `.streamlit/config.toml`); keep both CORS+XSRF `true` in `.streamlit/config.toml` (secure + no warning). A UI **Custom Start Command** overrides the config file, so it must also be clean/empty.
- Railway colors **anything on stderr red**. uvicorn/streamlit write their startup banner to stderr (e.g. "Uvicorn server started", "Application startup complete") — harmless, once per deploy, unremovable without custom framework log config. App logging is routed to stdout in [[git-sync-workflow]]-tracked commits (bot_app.py / api/main.py + `warnings.filterwarnings("ignore", FutureWarning)`).
- **Changing WEBHOOK_SECRET is safe**: the secret is part of the webhook URL path, so bot_app re-registers the Telegram webhook automatically on next deploy (URL changes → re-set). Must be ≥32 chars or bot_app logs a warning.
- Local dev uses Python 3.13.2; pytrends/Google-Trends fails on Railway datacenter IPs (Google blocks) — handled gracefully, Google Suggest still works.
- **DB migrations are applied MANUALLY (no auto-runner on deploy):** migration_*.sql files live in repo root; they are NOT run on Railway deploy. They're applied by editing `api/run_migration.py` (hardcoded to one filename) and running it locally — it connects to the Railway Postgres **public proxy** URL (`turntable.proxy.rlwy.net:18475`), not the internal `DATABASE_URL`. So when a `function/table/index does not exist` error shows in prod, the cause is usually an un-applied migration. migration_022 (perf indexes + `cleanup_expired_llm_cache()`) was applied 2026-05-28. As of commit 68f5cb7, `api/run_migration.py` reads the URL from env (`MIGRATION_DATABASE_URL`, stored in gitignored `.env`), takes the migration filename as an arg, and forces UTF-8 stdout (Windows cp1256 console crashes on emoji otherwise). Usage: `python api/run_migration.py <file.sql>`. **DB password rotated 2026-05-29** — the old password (still in git history pre-68f5cb7) is now INVALID, so that exposure is neutralized. **Rotation gotcha (cost real confusion):** changing Railway's `POSTGRES_PASSWORD` variable does NOT change the real role password — you must also run `ALTER USER postgres WITH PASSWORD '...'`, AND every app service has its OWN `DATABASE_URL` that needs updating (DealPulseKSA API reads it at [api/db.py] get_pool, dashboard at dashboard.py `_get_pool`). Both are now set as `${{Postgres.DATABASE_URL}}` references so future rotations auto-propagate. Symptom of a missed service: continuous `FATAL: password authentication failed for user "postgres"` in Postgres deploy logs. Also update local `.env` `MIGRATION_DATABASE_URL` + pgAdmin saved connection.
- **Two Postgres services existed; orphan deleted 2026-05-29:** the live DB is the **`Postgres`** service (proxy `turntable.proxy.rlwy.net:18475`, db `railway`, 59 tables). A stale orphan duplicate **`Postgres-Q8mB`** (28 tables, not wired to any service) was deleted — no impact. If two DB services ever reappear, the live one is the one the services + pgAdmin point to; never reference the wrong one or services connect to an empty DB.
- **Where secrets live (asked 2026-05-28):** Production tokens live ONLY in **Railway → service → Variables**, never in the repo or git history. Local `.env` holds only local-dev keys (BOT_TOKEN, DB, Cloudinary, DISCORD_WEBHOOK_URL, GROQ, JWT…). **Meta social tokens (`FB_PAGE_ID`, `IG_BUSINESS_ID`, `META_PAGE_ACCESS_TOKEN`, `THREADS_*`) are NOT in any local file or git — only Railway.** So "where's the working token?" → answer is always Railway Variables. (I do NOT store secret values in memory by design.) Meta `META_PAGE_ACCESS_TOKEN` must be a **Page token** from `GET /me/accounts`, not a User token, or FB/IG publishing returns HTTP 400. See [[bug-fixes-log]] #8.
- **Dashboard login on Railway**: there is no `.streamlit/secrets.toml` (gitignored), so dashboard.py auth falls back to **env vars `username`/`password`** (also `DASHBOARD_USER`/`DASHBOARD_PASSWORD`); password is hashed once per session for streamlit-authenticator, cookie_key derives from the password. Local dev still uses `secrets.toml`. Dashboard public URL: `dashboard-production-6e9f.up.railway.app` (Settings → Networking exposes port 8080). Empty streamlit widget labels (`st.radio("")`) log a red a11y warning even with `label_visibility="collapsed"` → always give a non-empty label.
